## 1. 🔴 Kritiek

### K1 — GA4/GTM laadt zonder cookietoestemming (AVG)

**Bestand:** `src/layouts/BaseLayout.astro`, blok "GTM script lazy-loaded", regels ±375–395.

```js
function loadGTM(){
  if (loaded) return; loaded = true;
  var s = document.createElement('script');
  s.src = 'https://www.googletagmanager.com/gtag/js?id=G-VS8SZZ6W45';
  ...
}
['scroll','mousemove','touchstart','keydown','click'].forEach(...loadGTM, {once:true});
requestIdleCallback(function(){ setTimeout(loadGTM, 3000); });
```

Er zit **geen consent-check** in `loadGTM()`. Ter vergelijking: Clarity (regel ±472) en Meta/LinkedIn (regel ±503) hebben die check wél (`localStorage.getItem('aanloop_cookie_consent') !== 'all'` → `return`). Dit is een overgeslagen copy-paste.

**Live gereproduceerd:** consent gewist → `/over/` geladen → op **"Alleen noodzakelijk"** geklikt → resultaat:
```json
{"consent":"necessary","gtmLoaded":true}
```

Consent Mode v2 staat wel default op `denied`, dus GA plaatst geen cookies. Maar het script wordt gedownload van Google (IP-overdracht) en cookieless pings vertrekken, zonder grondslag. Voor een bureau dat AVG-compliance verkoopt is dit het pijnlijkste type bevinding.

**Oplossing:** dezelfde guard bovenin `loadGTM()` zetten en na `setConsent('all')` een `loadGTM()`-aanroep toevoegen zodat toestemming direct effect heeft.

```js
function loadGTM(){
  if (loaded) return;
  try { if (localStorage.getItem('aanloop_cookie_consent') !== 'all') return; } catch(e) { return; }
  loaded = true;
  ...
}
```

### K2 — ElevenLabs-widget zet persistente identifier vóór consent

**Bestand:** `src/layouts/BaseLayout.astro:838-839`

```html
<elevenlabs-convai agent-id="agent_9701kqeqntncevw9dwe3fyc8ddpr"></elevenlabs-convai>
<script src="https://unpkg.com/@elevenlabs/convai-widget-embed" async></script>
```

Geen consent-gate. Live gemeten localStorage-sleutels bij eerste bezoek, vóór enige keuze:
```
["aanloop_exit_shown", "aanloop_cookie_consent", "elevenlabs_convai_user_id"]
```

`elevenlabs_convai_user_id` is een persistente identifier → toestemmingsplichtig (ePrivacy/AVG). Twee extra risico's in dezelfde regel: de bron is **`unpkg.com` zonder versiepin en zonder SRI** — elke upstream-wijziging draait direct in productie op alle 219 pagina's.

**Oplossing:** widget lazy laden achter de bestaande consent-helper, versie pinnen (`@elevenlabs/convai-widget-embed@<x.y.z>`) en bij voorkeur self-hosten. Als de widget functioneel noodzakelijk wordt geacht: dat expliciet in `/cookies/` onderbouwen.

## 2. 🟠 Hoog

### H1 — Twee cookie-banners op alle 219 pagina's

**Bestanden:** `src/components/Footer.astro:320` én `src/layouts/BaseLayout.astro:679`

Beide renderen `id="cookie-banner"`, `id="cookie-banner-title"` en `id="cookie-accept"`. Sitewide-scan: **219/219 pagina's hebben deze drie dubbele id's.**

Gevolgen:
- `document.getElementById('cookie-accept')` pakt altijd de eerste → beide scripts binden hun handler aan dezelfde knop.
- De BaseLayout-banner toont nooit; zijn `cookie-decline`-knop is onzichtbaar en dus onbereikbaar.
- Twee elementen met `role="dialog" aria-modal="true"` in dezelfde DOM.
- Inconsistente opgeslagen waarde: Footer schrijft `'necessary'`, BaseLayout `'functional'`. Alle gates elders vergelijken op `=== 'all'`, dus dit is nu onschadelijk — maar het is een tijdbom bij de volgende wijziging.
- Ongeldige HTML (dubbele id's).

**Oplossing:** één banner behouden. De Footer-versie is de werkende (focus-trap, Escape-afhandeling, Tab-cyclus). Verwijder het banner-blok + script uit `BaseLayout.astro` en verplaats de `gtag('consent','update',…)`-aanroep naar `hideBanner()` in `Footer.astro`.

### H2 — 404-pagina wordt niet geserveerd (lege respons)

`GET https://aanloopai.nl/wat-dan-ook/` → **status 404, body leeg (0 bytes)**. De bezoeker krijgt de browserfoutmelding, geen navigatie, geen merk, geen weg terug.

`dist/404.html` bestaat wél (111 KB, gebouwd). `src/worker.js:1253` valt terug op `env.ASSETS.fetch(request)`, en `wrangler.toml` mist de sleutel:

```toml

directory = "./dist"
binding = "ASSETS"
# ontbreekt: not_found_handling = "404-page"
```

**Oplossing:** `not_found_handling = "404-page"` toevoegen aan `[assets]`, of in de worker-fallback bij status 404 expliciet `/404.html` ophalen en met status 404 teruggeven.

### H5 — Contactformulier: geen validatie, geen honeypot

**Bestand:** `src/pages/contact.astro`

Het formulier heeft `novalidate` en het submit-script bevat geen enkele controle — het POST direct. Live getest met een leeg formulier:

```
POST /api/submit → 400
UI: "✗ Er is iets misgegaan. Probeer opnieuw of mail naar hello@aanloopai.nl."
```

De bezoeker die zijn naam vergat leest dus dat de site stuk is. Geen veldmarkering, geen `aria-invalid`, geen focusverplaatsing, en `#form-error` heeft geen `role="alert"` → schermlezers melden niets.

Twee vervolgproblemen:
- **Serverzijde valideert alleen het e-mailadres** (`src/worker.js`, `handleSubmit`: `if (!isValidEmail(userEmail))`). `name` en `message` mogen leeg zijn → lege lead in D1 + notificatiemail + autoresponder.
- **`botcheck` (honeypot) ontbreekt** in `contact.astro`. De vijf andere formulieren (`demo-aanvragen`, `gratis-ai-scan`, `ai-roi-calculator`, `ai-oplossing-matcher`, `ai-vindbaarheid/check`) hebben hem wél. De rate-limit (5 per 600 s per IP, `handleSubmit`) is de enige rem.

**Referentie-implementatie staat al in het project:** `demo-aanvragen.astro` doet het goed — `v1()`/`v2()` met per-veld foutelementen (`err-voornaam`, `err-achternaam`, `err-email`), `scrollIntoView` en een specifieke melding. Kopieer dat patroon naar `contact.astro`, voeg `botcheck` toe en breid `handleSubmit` uit met een `name`/`message`-check.

### H6 — "Exit-intent"-modal is een interstitial op 30 seconden

**Bestand:** `src/components/ExitIntentModal.astro:46`

```js
document.addEventListener('mouseout', function (e) { if (!e.relatedTarget && e.clientY <= 0) show(); });
setTimeout(show, 30000);   // ← dit is geen exit-intent
```

Staat op **alle 219 pagina's**, inclusief `/privacy/`, `/voorwaarden/` en `/tarieven/`. Live gezien: de modal dekte de complete prijstabel af terwijl er actief doorheen gescrold werd. Op mobiel valt dit onder Googles *intrusive interstitial*-criteria.

**Oplossing:** de `setTimeout`-trigger schrappen (alleen `mouseout` bewaren), of minimaal koppelen aan scrolldiepte >60% + niet tonen op prijs-, juridische en formulierpagina's.

### Nieuwe bevinding tijdens de deploy-verificatie: dubbele `Cache-Control`

Elk bestand kreeg twee `Cache-Control`-waarden achter elkaar, bijvoorbeeld
`/_astro/aanvragen.CsBWLcj2.css`:

```
Cache-Control: public, max-age=300, s-maxage=86400, stale-while-revalidate=604800, public, max-age=31536000, immutable
```

Oorzaak: Cloudflare past **alle** matchende regels uit `_headers` toe en voegt
gelijknamige headers samen met een komma. Het catch-all blok `/*` zette dus zijn
`max-age=300` vóór de `immutable` van `/_astro/*` — de jaarcache van de
content-hashed assets was daarmee in de praktijk 5 minuten.

Twee dingen kwamen bij het repareren aan het licht:

- **`cacheControlFor()` in `src/worker.js` is dode code voor statische bestanden.**
  De asset-laag serveert die zonder de Worker aan te roepen; `_headers` is de
  enige bron. Er staat nu een waarschuwing boven de functie.
- **Het `/*`-blok mag zijn `Cache-Control` niet kwijt.** Een eerste poging waarbij
  die regel verdween liet alle HTML terugvallen op de asset-default
  `public, max-age=0, must-revalidate` — de 24-uurs edge-cache verdween. Live
  gemeten en direct teruggedraaid.

Oplossing: `/*` houdt de HTML-default en élk specifieker blok begint met
`! Cache-Control`, wat die geërfde waarde weghaalt. Live geverifieerd, één waarde
per pad:

| Pad | `Cache-Control` |
|---|---|

### M7 LCP-preload — afgehandeld

De preload wees naar het logo mét `fetchpriority="high"`, terwijl de LCP op
desktop de hero-afbeelding is. Nu:

- `BaseLayout.astro` heeft een `preloadHero`-prop; alleen `index.astro` zet hem.
  Sitewide-controle op de build: 1 pagina met `imagesrcset`, en dat is `/`.
- De preload draait door `getImage()` met exact dezelfde `widths`, `sizes`,
  `format` en `quality` als het `<Image>`-blok in `Hero.astro`. Build-check:
  preload-`imagesrcset` is **teken voor teken gelijk** aan de `srcset` van de
  `<img>` — geen tweede download.
- `media="(min-width: 1024px)"`: de hero staat op `hidden lg:block`, dus onder
  1024px wordt er niets extra's opgehaald (daar is de h1 de LCP).
- De logo-preload blijft staan maar **zonder** `fetchpriority`, zodat die de
  echte LCP niet meer verdringt.

### L6 ElevenLabs-branding — onderzocht, actie bij M

De badge bestaat echt. Playwright op de live widget vindt in de shadow root een
link `https://elevenlabs.io/agents` met de tekst "ElevenAgents" en de zin
"Powered by ElevenAgents"; `BaseLayout.astro` (regel ±557) zet die op
`display:none`.

Gelezen: ToS (EEA — die geldt hier, M zit in NL), ElevenAgents Terms
(service-specific, precies dit product), OEM Terms, en de widget-documentatie.

| Bron | Bevinding |
|---|---|
| ToS (EEA) §5(b) | "any use of the Services other than as specifically authorized herein, without our prior written permission, is strictly prohibited" — brede restbepaling, noemt branding niet |
| ToS (EEA) §5(c) | Merken mogen niet worden "copied, imitated or used" — dat beperkt het **gebruiken** van hun merk, niet het verbergen |
| ElevenAgents Terms | Geen attributieplicht, geen co-brandingclausule, geen verbod op aanpassen van de widget |
| OEM Terms | Alleen voor Business Entities (Scale/Business/Enterprise); zwijgt over branding |
| Widget-documentatie | Geen brandingclausule en geen ondersteunde optie om de badge uit te zetten gevonden |
| Music API Terms (contrast) | Bevat wél een expliciete plicht: "you shall prominently co-brand ... 'powered by ElevenLabs'". ElevenLabs schrijft die clausule dus wanneer het dat wil — en heeft dat bij Agents niet gedaan |

**Oordeel: geel.** Geen aantoonbare schending in de teksten die op ons van
toepassing zijn, maar twee restrisico's: de brede formulering van §5(b), en de
mogelijkheid dat er via de documentatie tóch attributie geëist wordt (de Music API
Terms verwijzen expliciet naar "attribution(s) required ... in applicable
documentation"). Dat is geen juridisch advies.

Besluit van M: **schriftelijke bevestiging vragen, code voorlopig ongewijzigd.**
Concept-mail met de drie vragen staat klaar in `docs/elevenlabs-branding-vraag.md`,
inclusief wat er na elk mogelijk antwoord moet gebeuren.

#### Technische inperking — uitgevoerd

Los van de juridische vraag patchte het blok `Element.prototype.attachShadow`
**globaal**: élke shadow root op de pagina kreeg de verberg-CSS én een eigen
MutationObserver. Een later toegevoegd web component kon daardoor ongemerkt
elementen kwijtraken.

Eerst gemeten hoe de badge er werkelijk uitziet:

```
<p class="whitespace-nowrap …">Powered by ElevenAgents<a href="https://elevenlabs.io/agents">ElevenAgents</a></p>
   └─ zit in <div class="overlay …"> — daar zit de rest van de widget óók in
```

Daaruit volgden drie correcties:

- De patch doet nu alleen iets als `this.tagName === 'ELEVENLABS-CONVAI'`.
- De selectors `[class*="powered"]` en `[class*="branding"]` zijn geschrapt: ze
  raakten **nul** elementen in de widget. Wat overblijft is één regel,
  `p:has(> a[href*="elevenlabs.io"])`, plus de MutationObserver als vangnet voor
  late render en browsers zonder `:has()`.
- Alleen de `<p>` gaat weg, niet de `overlay`-container erboven. De `<a>` alleen
  verbergen zou de tekst "Powered by" laten staan.

Live geverifieerd na deploy:

| Meting | Resultaat |
|---|---|
| Vreemd web component (zelf aangemaakte shadow root met een elevenlabs-link) | `injectedStyles: 0`, link en span blijven `inline` — patch raakt het niet meer |
| Widget-shadow root | `injectedStyles: 1`, badge `display: none`, niet zichtbaar |
| `overlay`-container | nog steeds `flex` — widget zelf intact |
| Widget in beeld | launcher rendert normaal ("Hulp nodig? · Een gesprek starten"), geen badge |
| Page-errors | geen |
